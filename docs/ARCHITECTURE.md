# Архитектура SUSHIRIGA

## Слои

```
pages/        маршруты: собирают экран из features + components (тонкие)
features/     доменные модули: логика (чистые функции) + свои компоненты
components/   переиспользуемый UI без знания домена: ui/, layout/, book/
services/     доступ к данным за интерфейсами (mock сейчас → HTTP позже)
data/         статичные данные (меню, точки) до появления backend
i18n/         переводы lv/ru/en, типизированные ключи
types/        доменные типы (Product, Cart, Order, PromoCode, Review, Tip, Location…)
hooks/ utils/ styles/
```

Правило зависимостей: `pages → features → components/services → types/utils`.
`components/` не импортирует `features/` (кроме layout, которому нужна корзина для бейджа).

## Сервисы и будущий backend

Все внешние операции идут через интерфейсы в `src/services/*`:

| Сервис            | Сейчас                                                | Потом                                       |
| ----------------- | ----------------------------------------------------- | ------------------------------------------- |
| CatalogService    | `src/data` в бандле                                   | `GET /catalog` (админка управляет меню)     |
| LocationService   | `src/data/locations.ts`                               | API, несколько точек                        |
| OrderService      | `mock/`: расчёт как на сервере, заказы в localStorage | API: quote + заказ по вебхуку оплаты        |
| OrderAdminService | демо-кнопка «следующий статус»                        | админ-панель: статусы, время приготовления  |
| PromoService      | `mock/fixtures.ts`: коды `DEMO*`                      | API; финальная скидка считается на сервере  |
| PaymentService    | `mock/demoPaymentService` (деньги не списываются)     | Stripe: PaymentIntent на сервере для quote  |
| AuthService       | только гость                                          | любой провайдер, регистрация необязательна  |
| AssistantService  | rule-based по каталогу                                | LLM на backend, ответ = id товаров каталога |
| ReviewService     | localStorage, не публикуется                          | API + модерация                             |

Композиция — `services/createServices.ts`. Компоненты получают сервисы через `useServices()`,
поэтому замена реализации не трогает UI. В тестах сервисы можно подменить через `<AppProviders services={…}>`.

**Демо-режим** = `VITE_API_URL` пуст. На всех страницах виден баннер «Demo mode».

### Изоляция mock-кода

- Все mock/demo-реализации лежат только в `src/services/mock/` (см. `mock/README.md`).
- ESLint (`no-restricted-imports`) запрещает импортировать `services/mock` откуда-либо, кроме
  `createServices.ts` и тестов.
- Если задан `VITE_API_URL`, mock-сервисы **не подключаются**: заказы, оплата, промокоды, отзывы и
  ассистент получают реализации `notConnected*`, которые явно падают (до появления HTTP-слоя).
- `createDemoPaymentService` отказывается создаваться вне демо-режима.
- Заказ, оплаченный демо-оплатой, хранит `payment.provider = 'demo'`; страница заказа показывает
  предупреждение «деньги не списаны, ресторан заказ не получил».

## Деньги и модель доверия

Только целые **центы** (`Cents = number`). Форматирование — `Intl.NumberFormat` в `formatPrice`.
Цены в корзине всегда берутся из каталога, из localStorage — только `productId` + количество.

Браузеру **не доверяют** цены, скидки и суммы. Поток оформления:

1. `orders.quote(CheckoutRequest)` — браузер отправляет только `productId`, количество, промокод,
   чаевые, точку и время. Сервер сам считает цены, скидку и итог → `CheckoutQuote`.
2. Если промокод отклонён или итог отличается от показанного в корзине — оформление
   останавливается, клиент видит причину (никакой оплаты «другой суммы»).
3. `payments.pay({ quoteId, amount })` — платёж создаётся для quote; в Stripe сумму берёт сервер.
4. `orders.awaitPaidOrder(quoteId, payment)` — заказ существует только после подтверждения оплаты
   (в production его создаёт вебхук, клиент лишь получает результат). Mock-реализация проверяет,
   что платёж успешен и сумма точно равна quote, и не создаёт дубликатов для одного quote.

Те же правила (`cartMath`, `evaluatePromo`, лимит чаевых, статусы) должен реализовать backend.

## Книга (`components/book`)

- `bookModel.ts` — чистая геометрия: грани (face 0 = обложка), листы, развороты.
  Состояние — «якорная грань», поэтому при повороте телефона читатель остаётся на той же странице.
- `layout`: `single` (телефон) / `spread` (≥ 768px) / `auto`.
- 3D: `rotateY(-180deg)` вокруг корешка, `backface-visibility`, временный z-index для листающегося листа.
- Объём: закрытая книга показана в ракурсе 3/4 (`--tilt`), корешок (`.hinge`) прикреплён к листу
  обложки и уходит вместе с ней; под листами — блок страниц с видимым обрезом; при перелистывании
  по странице проходит тень (`.turning`). Слой `.mover` — плоская группа со своей перспективой,
  поэтому z-index листов продолжает работать.
- Ввод: свайп (Pointer Events), клавиши ←/→/PageUp/PageDown/Home/End, кнопки «Назад»/«Вперёд»,
  кнопка «Открыть» на обложке. Уголки страниц — **только для мыши** (`hover: hover` и
  `pointer: fine`) и только внутри поля страницы (`--page-pad-x`), поэтому никогда не перекрывают
  кнопки и текст. На телефоне их нет — там свайп.
- Размер: ограничен шириной **и высотой** экрана (`--chrome`), чтобы книга с кнопками помещалась
  на экран; блюд на странице: разворот — 4, телефон — 3 (высокий экран) или 2 (`useProductsPerPage`).
- Темы глав (`features/menu/bookThemes.ts`): цвет переплёта и узор тиснения (seigaiha, shippo,
  kikko, linen) для каждой категории — только оформление, данные меню не меняются. Тот же цвет
  используется на корешках полки, в навигации по главам и в плейсхолдерах фото.
- Доступность: невидимые страницы `inert`, номер страницы в `aria-live`, `aria-roledescription="book"`.
- `prefers-reduced-motion` → длительности 0, переключение мгновенное.
- Типографика страниц в `cqi` — масштабируется от размера страницы.
- У каждой категории своя книга (`CategoryBook`, на последней странице — переход к соседним главам),
  на главной — книга всего меню (`MenuBook`) с оглавлением, которое листает книгу к нужной главе.

## Заказ

Гостевой поток: Menu → Cart → Pickup → Contact → «Подарить улыбку» → Payment → Order.

- Время приготовления: **финальное время выбирает сотрудник** после получения оплаченного заказа —
  `OrderAdminService.acceptOrder(id, minutes)` (переход `PAID → ACCEPTED` без выбора времени невозможен),
  варианты 10…80 мин с шагом 5 (`PREPARATION_TIME_OPTIONS`). Позже время можно изменить
  (`setPreparationTime`, например вместе с `DELAYED`).
- До принятия `Order.preparationTime = null`, клиент видит стандартную оценку 30 мин
  (`STANDARD_PREPARATION_MINUTES`). Автоматических правил «большого заказа» нет — сознательно.
- Ранний слот самовывоза = сейчас + 30 мин, в пределах часов работы точки.
- Слоты самовывоза считаются по часам работы точки в её часовом поясе (`Europe/Riga`).
- Переходы статусов — таблица `ORDER_TRANSITIONS`; та же таблица должна жить на сервере.
- Отзыв — только для `PICKED_UP`; рейтинг никогда не выбран по умолчанию.

## Админка (будущее)

Маршруты зарезервированы в `ADMIN_ROUTES`, не зарегистрированы. План: отдельный lazy-чанк,
доступ только для персонала, работа через `OrderAdminService` и будущие CRUD-сервисы меню/промокодов.

## Точки (locations)

Все данные точки — в `Location` (адрес, часы работы по дням недели, часовой пояс, телефон/e-mail
опционально). UI и checkout работают со списком `listActive()`, поэтому вторая точка добавляется
одной записью в данных/БД — без изменения кода. Сейчас активна одна точка; вторая в UI не показывается.

## Промокоды

`percentage` / `fixed`, `minOrderValue`, `expiresAt`, `usageLimit`, `active`, `visibility`
(`public` — работает без регистрации; `personal` — привязан к `customerId` аккаунта).
Финальная скидка всегда пересчитывается на сервере; фронтенд показывает результат `PromoService`.

## Бонусы

Бонусной системы в проекте **нет** и не планируется.
